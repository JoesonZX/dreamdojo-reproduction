# 吞吐瓶颈排查与解决

记录把 LAM 训练从"6+ 小时跑不完"调到"1–2 小时内完成"的完整排查。共两轮：
**Round 1 = 数据加载瓶颈，Round 2 = 计算/梯度累积瓶颈**。外加一节"监控与测量的坑"。

## 0. TL;DR

| 阶段 | 单步耗时(4路并行) | GPU 利用率 | 10k 步 ETA |
|------|------|------|------|
| 初始（1080p mpeg4 + accum6/batch16） | ~1.5 s/步，且前期卡死 | 0–5% | 6+ 小时 |
| Round 1 后（240p 转码 + dataset 优化） | 仍 ~1.5 s/步 | ~50% | ~6 小时 |
| Round 2 后（accum1 / batch32） | **实测 0.35 s/步（2.82 步/s）** | 60–100% | **~1 小时**（实测 2000 步/708s） |

两个独立瓶颈，必须都修：**数据**（Round 1）让 GPU 不再挨饿；**梯度累积空耗 + 并发争用**（Round 2）让墙钟真正降下来。

---

## 1. 症状

四个 run 并行启动后配置正确、无报错，但 **GPU 利用率 0–5%**，日志长时间停在
`Starting training from step 0`。典型的"GPU 算得快、在等数据"。

---

## 2. Round 1 — 数据加载瓶颈

### 2.1 诊断
- 排除崩溃：tmux/日志/GPU 显示进程都活着、无报错，只是慢。
- 对 `__getitem__` 直接计时：

  | 场景 | 耗时 | 说明 |
  |------|------|------|
  | 四路并行训练**进行中** | **1540 ms/样本** | 真实拖慢值 |
  | 杀掉训练后**隔离** | 42 ms/样本 | 单流并不算慢 |
  | `_frame_count` 单独 | 40 ms/次 | 每次 `__getitem__` 都重复调，冗余但非主因 |

  → 1540ms 主要来自**并发争用**，不是单次解码。

- `ffprobe` 查规格：**1920×1080 mpeg4**。三重叠加：①1080p 解码 CPU 重；
  ②mpeg4 关键帧稀疏 → 随机 seek 慢；③**4 run × 8 worker = 32 个 1080p 解码进程**
  抢 CPU/内存带宽 + 冷盘缓存。
- 为何原版没暴露：DreamDojo 用 700M 大模型，前向慢掩盖了数据慢；本实验小模型(60M)前向极快，瓶颈裸露。

### 2.2 候选方案基准（隔离，12 个真实视频）

| 方案 | 耗时 | 吞吐 |
|------|------|------|
| 当前（开2次 + 2次单帧 seek） | 42.1 ms | 23.8/s |
| 开1次 + `get_batch([t,t+skip])` | 34.8 ms | 28.7/s |
| opencv seek | 49.7 ms | 20.1/s |
| **240p 全关键帧转码 + get_batch** | **5.8 ms** | **172.7/s** |

单文件 5.3MB→0.70MB（约 1/7.5）。

### 2.3 解决
1. **预转码 `transcode_240p.sh`**：3243 个视频 → 240p 全关键帧(all-intra, GOP=1) h264；
   居中裁剪 4:3（匹配 `_center_crop_resize`）后缩放 320×240；HDF5 软链接到新目录
   `data/egodex/test_240p/`；`-vsync 0` 保帧数。结果 15GB→**2.7GB**，3243/3243 成功，
   0 失败，逐帧对齐校验通过；耗时 ~75 秒（24 并行）。
2. **dataset.py 三处优化**：decord bridge 改 `native`；`_load_pair` 单次开 + `get_batch`；
   帧数 `n` 缓存进 index，`__getitem__` 不再重复开视频。
3. **config** 的 `data_root` 指向 `test_240p`。

### 2.4 结果
`__getitem__` 隔离 42ms→**8.8ms（114/s）**；GPU 利用率 0–5%→~50%。
但**四路并行单步仍 ~1.5s/步，10k 步 ETA 仍 ~6 小时** → 还有第二个瓶颈。

---

## 3. Round 2 — 计算 / 梯度累积瓶颈

### 3.1 诊断（用 checkpoint mtime 取地面真值）
数据修好后仍慢。看**磁盘 checkpoint**（不受日志缓冲影响）：step 2000 落盘后 41 分钟仍无
step 4000 → ≥1.2 s/步，与日志吻合。GPU 利用率只有 ~30%、显存仅 6.8/49GB → 既没吃满算力、也没吃满显存。

### 3.2 compute-vs-data 基准（单卡隔离, bf16）

| | batch 16 | batch 32 | batch 64 |
|------|------|------|------|
| 纯计算 fwd+bwd | 78 ms | 165 ms | 366 ms |
| 全流程（8 worker+数据） | **81 ms** | — | 395 ms |

两个关键结论：
1. **隔离时数据已被完全隐藏**（81ms ≈ 78ms）——Round 1 之后数据不再是瓶颈。
2. **真正的墙钟杀手是 `grad_accum=6`**：一个优化步要做 6 次前向反向 = 6×78ms ≈ **0.47s/步（隔离）**；
   再叠加 4 路 CPU/带宽争用（×~3）→ **~1.5s/步**。即 accum 把每个"记录步"的计算量放大了 6 倍，纯属空耗。

### 3.3 解决
改 4 个 config（**四个 run 完全一致，对照公平不受影响**）：

| 参数 | 旧 | 新 |
|------|----|----|
| gradient_accumulation_steps | 6 | **1** |
| per_gpu_batch_size | 16 | **32** |
| total_steps | 20000 | **10000** |
| num_workers | 8 | 10 |

- 有效 batch 96→32：本模型用 LayerNorm（无 BatchNorm），无 batch 统计问题；梯度略噪但无害；
  lr 2.5e-5 保守，沿用即可。
- 解耦损失(exp3)是 batch 内交叉协方差，batch 32 估计略噪但仍有效。
- 样本预算 192万→32万：PSNR 在 ~19万样本即达 28dB，动作/解耦监督每步生效，10k 步足够显现效果。
- 重启前清掉旧 `step_*`，否则会被 `resume_from_checkpoint` 自动续训（混入旧配置）。

## 4. 监控与测量的坑（debug 过程踩到的）

- **stdout 块缓冲**：`python ... | tee log` 时 Python 对管道是**块缓冲**（~8KB）。`log_every=100`
  时每 100 步才 1 行，accum1 下要上千步才凑满一个缓冲块刷盘 → **日志文件长时间空白**，看起来像卡死，
  其实在跑。**教训：用 checkpoint（落盘、无缓冲）或 `nvidia-smi` 利用率判断进度，别只看日志**；
  未来重启可在命令前加 `PYTHONUNBUFFERED=1` 或 `python -u`。
- **冷启动**：前 ~100 步因 worker 拉起 + cudnn autotune 偏慢，之后提速 → 早期"等 step-100"会误判超时。
- **微基准要对齐真实精度**：fp32 微基准 489ms/microbatch，但真实训练走 **bf16**（78ms），差 6 倍；
  测吞吐务必同精度（`torch.autocast(bf16)`）。
- **隔离 vs 并发**：单流基准好看不代表并发不崩；务必在"目标并发度"下测，或用 checkpoint 实测墙钟。

---

## 5. 最终配置（4 个 run 一致）
small model（512/8/8）· bf16 · batch 32 · accum 1 · 10k 步 · lr 2.5e-5 · warmup 1000 ·
数据 `egodex/test_240p` · seed 42。

## 6. 对实验公平性的影响：无
帧数、采样索引、动作标签、动作归一化统计全部不变；画质 1080p→240p、有效 batch/步数变化
**对四个 run 一视同仁**。消融比的是相对差异，结论严格可比。
